# Сущности под контракт панели

Панель проверяет ответы zod-схемами из `panel/src/schemas`. Схемы помечены `.loose()`, то есть
лишние поля проходят, а недостающие обязательные — ломают разбор. Поэтому наша модель описана
так, чтобы существующие схемы оставались валидными, а свои поля добавлялись сверху.

## Решение об именах

Имена полей у 3x-ui чужие для нашей задачи: `email` — на деле имя клиента, `uuid` — ключ,
`protocol` — понятие Xray. Переименование стоит около 400 правок по коду: `email` 125 мест,
`expiryTime` 100, `protocol` 65, `subId` 49, `totalGB` 39, `limitIp` 28.

Имена оставляем, смысл переопределяем. Пользователь видит подписи из `web/translation/en-US.json`,
а не имена полей, поэтому в интерфейсе всё будет названо по-нашему.

| Поле в API | Что означает у нас |
|---|---|
| `email` | имя клиента |
| `uuid` | ключ клиента, он же токен в `qd://` |
| `totalGB` | лимит трафика в байтах, 0 — без лимита |
| `expiryTime` | срок действия, unix-мс, 0 — бессрочно |
| `limitIp` | лимит одновременных устройств |
| `group` | имя группы точек входа |
| `inboundIds` | точки входа, назначенные напрямую |
| `protocol` | всегда `qd`, оставлено ради схемы |
| `subId` | не используется, подписки вырезаны |

## Узел

Соответствует `NodeRecordSchema`. Узел — машина с XDP-датапасом.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | number | внутренний идентификатор |
| `name` | string | тег узла, `node-1` |
| `address` | string | адрес узла, домен или IP |
| `enable` | bool | участвует ли в сети |
| `apiToken` | string | админский ключ **этого** узла, свой у каждого |
| `status` | string | `online` / `offline` / `unknown` |
| `latencyMs` | number | отклик по управляющему каналу |
| `cpuPct`, `memPct`, `uptimeSecs` | number | состояние машины |
| `panelVersion` | string | версия `qd-node` |
| `inboundCount` | number | сколько точек входа на узле |
| `clientCount`, `onlineCount` | number | клиенты, привязанные и активные |
| `lastHeartbeat` | number | unix последнего ответа |
| `lastError` | string | текст последней ошибки |

Наши поля сверх схемы:

| Поле | Тип | Смысл |
|---|---|---|
| `role` | enum | `ingress` или `egress` |
| `addressV6` | string | адрес IPv6 узла |
| `shapeMbit` | number | ограничение узла целиком, 0 — без ограничения |
| `natEntries` | number | занято записей трансляции |
| `sessions` | number | активных сессий на узле |

Поля `scheme`, `port`, `basePath`, `xrayVersion`, `depletedCount` схема допускает пустыми —
отдаём нули и пустые строки.

## Точка входа

Соответствует разделу Inbounds. Точка входа — порт на узле, к которому подключается клиент.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | number | идентификатор |
| `nodeId` | number | на каком узле |
| `port` | number | порт UDP |
| `remark` | string | человеческое имя |
| `enable` | bool | принимает ли подключения |
| `shapeMbit` | number | ограничение скорости точки входа |
| `up`, `down` | number | трафик через точку входа |
| `clientCount` | number | сколько клиентов её используют |
| `protocol` | string | всегда `qd` |

Порт уникален в пределах узла — проверка уже реализована в форме.

## Группа

Смысл меняется против оригинала: у 3x-ui группа объединяет **клиентов**, у нас — **точки входа**.
Группа назначается клиенту вместо перечисления точек входа поимённо.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | number | идентификатор |
| `name` | string | имя, его хранит `client.group` |
| `entrypointIds` | number[] | входящие точки входа |
| `clientCount` | number | сколько клиентов ссылается |

Группа считается назначаемой, если в ней есть хотя бы одна включённая точка входа.
Клиент получает либо `group`, либо `inboundIds`; если заданы оба, старше группа.

## Клиент

Соответствует `ClientRecordSchema`.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | number | идентификатор |
| `email` | string | имя клиента |
| `uuid` | string | ключ, попадает в `qd://` |
| `enable` | bool | доступ разрешён |
| `comment` | string | заметка |
| `group` | string | имя группы точек входа |
| `inboundIds` | number[] | точки входа напрямую |
| `totalGB` | number | лимит трафика в байтах |
| `expiryTime` | number | срок действия |
| `limitIp` | number | лимит устройств |
| `traffic.up`, `traffic.down` | number | израсходовано |
| `traffic.lastOnline` | number | последняя активность |
| `createdAt`, `updatedAt` | number | отметки времени |

Наши поля сверх схемы:

| Поле | Тип | Смысл |
|---|---|---|
| `devices` | array | отпечаток, платформа, первое и последнее появление |
| `lastNodeId` | number | через какой узел заходил последний раз |

## Что отдавать по эндпоинтам

Реализуем только то, что нужно оставленным разделам. Остальные пути панель не вызывает,
потому что соответствующие страницы вырезаны.

**Узлы:** `nodes/list`, `nodes/add`, `nodes/update/:id`, `nodes/del/:id`, `nodes/test`.

**Точки входа:** `inbounds/list`, `inbounds/list/slim`, `inbounds/options`, `inbounds/add`,
`inbounds/update/:id`, `inbounds/del/:id`, `inbounds/bulkDel`, `inbounds/resetAllTraffics`.

**Клиенты:** `clients/list`, `clients/list/paged`, `clients/add`, `clients/update/:id`,
`clients/del/:id`, `clients/bulkDel`, `clients/bulkAdjust`, `clients/bulkResetTraffic`,
`clients/onlines`, `clients/lastOnline`, `clients/activeInbounds`, `clients/delDepleted`.

**Группы:** `clients/groups`, `clients/groups/create`, `clients/groups/rename`,
`clients/groups/delete`, `clients/groups/bulkAdd`, `clients/groups/bulkRemove`.
Участники групп — точки входа, а не клиенты, но пути оставлены прежними.

**Состояние и обслуживание:** `server/status`, `server/getNewUUID`, `settings/all`,
`csrf-token`, `login`, `logout`. Бэкап переехал на узлы — `backup/pull`, `backup/restore`.

**Публикация:** `publish/draft`, `publish/discard`, `publish/plan`, `publish/push`,
`publish/apply`, `publish/status`.

**Не реализуем:** всё про Xray — `restartXrayService`, `stopXrayService`, `xrayMetricsState`,
`xrayObservatory`, `getXrayVersion`, `getConfigJson`, генераторы ключей Reality и ECH,
`custom-geo/*`, `updateGeofile`, `backuptotgbot`.

## Открытые вопросы

1. **Где живёт панель.** Решено: на машине администратора. Панель не слушает ни одного
   порта, конфиг уезжает пушем, состояние тянется опросом, клиенты панель не видят.
2. **Ключ клиента и подпись пакетов.** Сейчас датапас доверяет номеру сессии. Как только
   появится подпись, `uuid` станет ключом сессии, и его смена должна выселять клиента немедленно.
3. **Учёт трафика.** Счётчики живут в картах XDP и обнуляются при перезагрузке программы.
   Нужен перенос в базу с накоплением.

## Хранилище

Панель живёт на машине администратора и ничего не слушает. Узлы исполняют то, что им
отдали. Значит баз две, разной формы, и одна получается из другой.

### База панели

Внутри неё два несмешиваемых типа данных.

**Конфигурация** — течёт панель → узел, правится администратором, версионируется ревизией.

| таблица | поля |
|---|---|
| `nodes` | `id`, `tag`, `address`, `port`, `role`, `admin_key`, `shape_mbit`, `enable` |
| `entrypoints` | `id`, `node_id`, `port`, `remark`, `enable`, `shape_mbit` |
| `groups` | `id`, `tag`, `allow_exit` |
| `group_entrypoints` | `group_id`, `entrypoint_id` |
| `clients` | `id`, `tag`, `uuid`, `enable`, `expiry_at`, `comment`, `group_id` |
| `revisions` | `number`, `created_at`, `published_at` |

**Телеметрия** — течёт узел → панель, только на чтение, накапливается, наружу не уходит.

| таблица | поля |
|---|---|
| `client_traffic` | `client_id`, `node_id`, `up`, `down`, `epoch`, `at` |
| `devices` | `client_id`, `fingerprint`, `platform`, `first_seen`, `last_seen`, `up`, `down`, `node_id` |
| `ip_log` | `client_id`, `fingerprint`, `ip`, `node_id`, `last_seen` |
| `node_metrics` | `node_id`, `metric`, `t`, `v` |

Разделение не косметическое. Публикация сериализует только конфигурационную половину;
телеметрия на узел не возвращается никогда. И `publish/discard` откатывает только её же —
выбросить черновик и потерять собранную статистику невозможно.

Поле `epoch` в `client_traffic` — номер запуска датапаса на узле. Счётчики в картах XDP
обнуляются при перезагрузке программы, поэтому дельта считается только в пределах одной
эпохи; сменилась — новое значение прибавляется целиком. Без этого перезапуск узла даёт
отрицательную дельту и молча съедает период (открытый вопрос 3).

### База узла

Две формы, по роли. Обе несут `revision` и `self`.

**ingress**

| таблица | поля |
|---|---|
| `self` | `node_id`, `role`, `shape_mbit`, `encap_overhead` |
| `entrypoints` | `port`, `shape_mbit` — только свои |
| `clients` | `uuid`, `enable`, `expiry_at`, `allow_exit` |
| `peers` | egress: `node_id`, `address`, `port`, `key` |
| `admins` | `uuid` |

**egress**

| таблица | поля |
|---|---|
| `self` | `node_id`, `role`, `shape_mbit`, `encap_overhead` |
| `entrypoints` | `port`, `shape_mbit` |
| `peers` | ingress: `node_id`, `key` — кому разрешено подключаться |
| `admins` | `uuid` |

Таблицы `clients` у egress **нет** — не пустая, а отсутствует. Он клиентов не авторизует,
значит и знать их не должен.

`allow_exit` у клиента — проверяющая сторона той метки маршрутизации, что ставит клиент.
Клиент просит выход, ingress сверяет с правом. Без этого настройка выхода в группе
декоративна.

`encap_overhead` отдаётся узлу, а не хардкодится: у ingress в цепочке инкапсуляций две,
и MSS клампить надо по суммарной.

### Проекция

Одна чистая функция `project(node, state) → config`, единственная точка, где решается
что кому. Внутри — **перечисление того, что кладём** для каждой роли, не исключения.
Забыть включить можно, забыть исключить — нет.

Инвариант проверяется тестом, а не внимательностью:
- ни одна egress-проекция не содержит ни одного `uuid` клиента;
- ни одна проекция не содержит ключ чужого узла.

### Бесшовное применение

Узел кладёт присланную ревизию рядом с текущей. `apply` — атомарный `rename`, затем
перечитывание карт **разницей**, а не перестроением.

Перестроение недопустимо: очистка карт NAT и сессий рвёт все установленные соединения.
Применение, стоящее пользователям всех сессий, бесшовным не является. Добавить новых
клиентов, снять отозванных, остальных не трогать.

### Администратор

ingress принимает клиентов и админов, egress — только ingress-пиров и админов.

Администратор опознаётся **парой ключей**, а не общим секретом. Узел хранит открытую
половину, закрытая живёт только в клиенте администратора. Открытый ключ одинаков на всех
узлах и это безопасно именно потому, что он открытый: изъятый узел не отдаёт ничего.

Скрипт деплоя несёт `--admin-pubkey`; `nodes.admin_key` хранит открытую половину; пара
рождается при первом запуске панели, а не при заведении узла. Разбор трёх рассмотренных
форм и порядок восстановления доступа — в `client.md`.

Подключение панели к узлам — отдельный поток на том же транспорте, что и туннель, вне
пользовательского туннеля: трафик системы через него не идёт.

## Контрольный канал

**Только UDP и только наш транспорт.** Туннель, приветствия, обновление подписки и
управление узлом — один и тот же кадр на один и тот же порт. Разница между ними — поле
`kind` внутри зашифрованного заголовка, а между клиентом и администратором — длина
предъявленного токена: клиентский короткий, админский заметно длиннее.

Вариант с TCP/TLS на том же порту и сайтом-заглушкой рассматривался и **отвергнут**.
Он давал готовые надёжность и шифрование, но ценой второго протокола, второго стека
аутентификации и открытого TCP-порта, который надо чем-то правдоподобно занимать.
Одна дверь вместо двух: то, что не расшифровалось нашим ключом, узел роняет молча.

### Формат кадра

```
[0:8]    nonce      — открытый, случайный на каждый пакет
[8:64]   ChaCha20(key, nonce) ⊕ ...
   [8:12]   session — производная от токена
   [12:16]  seq
   [16]     kind: 1 туннель, 2 ping, 3 pong, 4 cancel, 5 управление,
            6 замер размера, 7 ответ на замер
   [17:20]  резерв
   [20:64]  начало внутреннего пакета — его IP/TCP/UDP заголовки
[64:]    данные внутреннего пакета как есть
```

Один блок ChaCha20 на пакет накрывает наш заголовок и заголовки внутреннего. Полезные
данные не шифруются: внутри и так либо TLS, либо то, что от шифрования не выиграет, а
двадцать раундов на каждый килобайт стоят полосы. Наружу видно только UDP со случайными
байтами — ни адресов внутри, ни счётчиков, ни признака, что это туннель.

Токен целиком уходит только в кадрах `kind = 5` и в приветствии. В туннельных вместо
него `session` — четыре байта, по которым узел находит клиента у себя. Гонять тридцать
два байта токена в каждом пакете при десятках тысяч пакетов в секунду смысла нет.

Ключ сети один на все узлы и выдаётся при деплое. Это слой маскировки, а не
аутентификации: тем, кто клиент и что ему положено, распоряжается токен внутри.

### Оверхед и MTU

Заголовок стоит 20 байт вместо 8. Итог: `MTU = PMTU − 20 (внешний IP) − 8 (UDP) − 20`.
Прошивать константу нельзя — на замеренном канале PMTU оказался 1480 (провайдерский
IPoE режет 1500 до 1480), в мобильной сети будет меньше, за чужим PPPoE своё. Клиент
меряет путь сам: бинарный поиск кадрами `kind = 6` с запретом фрагментации, узел
отвечает `kind = 7` тем же размером, так что подтверждается путь в обе стороны.
Перемеряется при смене сети — другой путь несёт другой размер, а туннель, оставшийся
слишком крупным, встаёт молча вместо явной ошибки.

Замер намеренно вынесен в **отдельный `kind`, а не в приветствия**. Зонд, не прошедший
по размеру, — нормальный и ожидаемый исход поиска; если бы им занимался тот же кадр,
что следит за живостью, сторож принял бы это за смерть узла и оборвал рабочий туннель.

### Следствие для API

Управляющий API узла — тот же контракт, что и у панели, но переносится кадрами
`kind = 5`, а не HTTP поверх TLS. Один формат на оба направления вместо протокола
плюс API.

Аутентификация клиента туннеля к этому отношения не имеет: она остаётся в UDP-датаплейне
и решается отдельно (открытый вопрос 2).

### Обрыв посреди публикации

Присланная ревизия складывается на узле рядом с текущей и до `apply` не действует.
Обрыв на `push` оставляет неполный файл — он просто не станет полным и не будет
применён: `apply` активирует только ревизию, чья контрольная сумма сошлась. Повтор
догружает её заново, состояние узла при этом не менялось ни на секунду.
